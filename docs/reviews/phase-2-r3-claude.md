## Three riskiest things

1. **An edit that reaches the editor after a rename's barrier, from a non-keyboard source.** During a rename the rename input holds focus, so the only such sources are asynchronous ones, such as an image paste whose `save_image` resolves late. That edit is outside every barrier. `commitRename` (App.tsx:222-243, `read_doc` :236, `rename_file` :238) computes `rewritten` from a `read_doc` taken after the flush and installs it with `rename_file`. Suppose the edit's 500 ms autosave fires between that `read_doc` and `rename_file`: `pathRef` is still the old path, the read equals `known`, so `write_doc` lands at the old path. `rename_file` then installs the stale `rewritten`, which lacks the edit, and the sync is clean (that write succeeded). So `renamed()` (document-sync.ts:331-333) reloads the disk bytes over the editor. The edit is lost silently. This needs an image-bearing document and a timer firing inside one IPC. It was not reproduced, because the r3a row forbids new probes. It is the same class as the barrier-to-discard backlog line, through the rename's read-then-write rather than a discard. The Phase 3 editor lock should cover it if the lock spans the rename's whole IPC sequence, not just the flush.
2. **The barrier-to-discard window for a switch spans two IPCs, not "one JS task".** Line V1.1-BACKLOG.md:165 describes the gap as one JS task. In `openFile`, `await loadDocument(path)` (`read_doc` + `read_sidecar`, App.tsx:152; DocumentPane.tsx:36-45) runs between the barrier's `saved` and the pane's replacement. An edit in that window is disposed with the pane (`key={openDoc.id}`). Keyboard input cannot reach the editor then: the tree entry that was clicked has `tabIndex={0}` (FileTree.tsx:84) and takes focus. The premise therefore holds for typed text, but the Phase 3 lock must last until `showDocument`, not until `flush` resolves. The same holds for close: an edit landing during the `appWindow.destroy()` IPC is lost.
3. **The W2 adoption rebuilds the editor, and the conflict branch is unguarded.** For a dirty rename whose rewrite changes the text, `reloaded(rewritten)` builds a new store and view. Undo history is dropped and the caret goes to the start of the document (journal-main.md:440, 2.27's own reading). Undo past a rename is gone, against the §6.5 single-stack model. Separately, document-sync.ts:330 (`renamed` while a conflict stands) is uncovered. In that branch the dirty editor keeps the old stem, and Keep mine would write `assets/<old>/` over the moved assets. Reaching it needs a conflict raised between the barrier and `renamed()`, which in turn needs the risk-1 edit. The macOS `editor-astral-between-runs.spec.ts:162` Backspace flake also cost this gate one rerun. It is the class's second macOS instance at this spec.

## Class-level lessons (for docs/lessons.md)

- LESSON: a caller that reads the disk after a barrier and writes those bytes back later (rename's `read_doc` → `rename_file` with `rewritten`) reopens the generation race the barrier just closed, because the sync's autosave can write between the read and the write → a caller's read-then-write of the open document runs inside the sync's serialised owner, or its write is refused when the sync's `known` moved since its read.
- LESSON: a backlog premise that sizes a race window ("one JS task") was written from one caller and is false for another (`openFile` awaits two IPCs inside it) → a window disposition names the awaited calls inside the window for each caller class, so the trigger task's fix spans the longest one.
