## Findings (≤ 20, most severe first)

Severity, rated by the consequence for the gate's criterion and never by the size of the fix (DECISIONS #review-1-r1): **blocker** — a gate criterion is not met, or wrong output reaches the user silently (example: Copy Markdown puts stale text on the clipboard and reports "Copied"); **should-fix** — a defect or a missing guard the phase should not close with, while the criterion still holds or the path is not the gate's own instrument (example: a redo chord bound under two names with no test that reads the binding table, so deleting one name stays green); **nit** — wording, citations, style, or an assertion with no behaviour behind it (example: `expect(checked).toBe(Object.keys(index).length)` where both sides are the same list). Mark a should-fix **Required** when the reconciliation should fail without it.

1. **blocker** — `apps/desktop/src/workspace/document-sync.ts:184` — `flush()` can authorize discarding a document while a newer edit remains unsaved. `write()` captures the generation, correctly leaves `dirty` true when another edit arrives during `await io.write`, but unconditionally returns `saved`; `flush()` at line 292 returns that without checking again. `App.tsx:112` destroys the window on this result, and `openFile` similarly replaces the pane. Reproduction against the unmodified module: mark the document dirty, call `flush()`, hold its write promise, type another character via `edited()`, then release the write. `/report/probes.log:1` reports `saved`, `dirty:true`, disk `first edit\n`, editor `first edit plus later keystroke\n`. Disposal then removes the later edit's timer. This reopens U1/U2 for edits during the barrier rather than before it. Fix: make flush drain subsequent dirty generations until the current generation is persisted, or return a checked non-success while still dirty; callers must also prevent new edits between their successful barrier and the actual state discard. Add delayed-write tests with an edit during flush and an action-level close/switch test asserting the last edit on disk.

2. **blocker** — `apps/desktop/src/workspace/document-sync.ts:305` — a user edit during rename silently restores obsolete image URLs on the next autosave. `App.tsx:236`–242 awaits the read, rename and tree refresh after flushing, with the editor still writable. If an edit arrives in that interval, `renamed()` adopts the rewritten disk bytes as `known` but deliberately retains the dirty editor containing the old asset stem. The next save passes the disk comparison and overwrites the rewritten URLs. `/report/probes.log:2` reproduces a clean flush of `![image](assets/a/x.png)`, a subsequent edit, the rename's disk rewrite to `assets/b/`, `renamed()`, and another flush: disk ends with `assets/a/x.png`, result `saved`, conflict false. The assets have moved to `assets/b`, so reopening renders a broken image. The existing test `tests/document-sync.test.ts:498` enshrines the overwrite using abstract `a`/`b` strings instead of the image relation. Fix: hold editing/autosave under the rename lifecycle until the path and rewritten editor state are adopted, or apply the same URL transformation to the live dirty document while preserving the concurrent edit. Replace that guard with an image-bearing document, an edit between pre-rename flush and completion, a subsequent save, and assertions that both the edit and new asset path survive and the image resolves after reopening.

3. **should-fix** — `apps/desktop/src/workspace/document-sync.ts:180` — a sidecar I/O failure after a successful Markdown write resets the Markdown baseline to bytes no longer on disk, so the next save raises a false external conflict. `DocumentPane.tsx:135` writes Markdown before `read_sidecar` and `write_sidecar`; either later IPC can reject. The sync catch restores `previous` for every rejection. `/report/probes.log:3` uses that exact partial-success contract: first flush fails after installing `edited\n`; retry returns `conflict` even though disk equals the editor and no external writer exists. This suspends further autosave behind “Changed on disk” after the original error is repaired. Fix: report Markdown and sidecar completion separately, keep the Markdown baseline at successfully written bytes, and retain the sidecar failure as retryable work. Add one test each for sidecar-read and sidecar-write failure after Markdown success, followed by successful retry without Reload/Keep mine.

The probes use injected I/O with controlled scheduling, not native timing claims. `/report/probes.mjs` is reproducible; `/report/document-sync.mjs` is TypeScript's ES2022 transpilation of the unchanged implementation. Existing deferred findings are cited as limitations above rather than counted again. Verdict: **FAIL**, two blockers, one should-fix, zero nits.

## Three riskiest things

1. Save completion and permission to discard state are different conditions while editing remains possible during IPC. The current close/switch tests edit before the action, not during its awaited write.
2. Rename changes disk paths, Markdown destinations and the editor's document across separate asynchronous steps. The dirty-buffer branch currently preserves text by undoing the asset rewrite.
3. Markdown and sidecar writes can succeed independently, but one rejected promise resets their shared success assumption. Phase 3's planned sidecar editing will also need to resolve the explicitly backlogged split between the pane baseline and document store.

## Class-level lessons (for docs/lessons.md)

- LESSON: A save result can describe an older generation while the current document is still dirty → assert that every success permitting disposal covers the latest generation, with edits injected during awaited writes and before disposal.
- LESSON: Preserving a concurrent dirty buffer across a structural disk change can restore stale references → test the relationship between edited content, rewritten destinations and moved assets through the next save and reopen.
- LESSON: One promise spanning several file writes hides partial success → track each persisted baseline independently and test failure after every successful preceding write, including recovery without an external conflict.
