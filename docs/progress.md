Notes: the design decision a reviewer should check — "break and take as one operation" is implemented as a compare-and-swap, not merely as "the rename succeeded". A bare rename is not sufficient: two processes recovering from the same crash can both see the stale file, the first renames it away and re-creates the lock with its own token, and the second's rename then succeeds against the *live* lock. So after the rename the stashed bytes are compared with the bytes that were judged stale; on a mismatch the file is renamed back (only while the lock path is still free — otherwise the stash is removed and the message says so) and a `RalphError` aborts this process, leaving the concurrent breaker the sole holder. The post-acquisition token re-read is the second, independent guard for the residual window between `openSync(lock, "wx")` and the first read. Both guards abort rather than retry, per the task text ("abort if it is not yours"): a process that discovers it is racing another breaker over the one lock must not keep trying, and the runner's callers all treat a `RalphError` as a stop. The alive-holder branch keeps its timeout/`Atomics.wait` behaviour unchanged, and a lock that disappears under the staleness read (`holder === null`) simply retries the create. New test file rather than an addition to `conformance.test.mjs`: those are fixture-repository scenarios driven through `ralph.sh`/`gate.sh`, and neither property here is observable that way — who owns the lock at a given instant needs a second actor interleaved at an exact point, and the syscall order needs the syscalls themselves recorded. Honest limit: `fsync` durability is asserted as the call order against an injected fs, not as a power-loss experiment; the real-fs leg of that test only proves the bytes land and no temporary file is left behind. The directory `fsync` is best-effort by design (a `catch` that swallows an `openSync(dir, "r")` refusal on platforms that do not permit it); the container is Linux, so the swallowing branch is not exercised here and no macOS or Windows claim is made.
