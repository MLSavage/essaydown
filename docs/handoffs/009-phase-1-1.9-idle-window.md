- **`&#x20;` mechanism, confirmed on the tree (principal, 2026-09-09).** `packages/core` `format(parse("Hello \n\n- a \n- b\n"))` returns `Hello\n\n- a\n- b\n`: micromark drops trailing spaces at parse, so the corpus invariants never see one. The editor path is different: a ProseMirror text node keeps its trailing space, and `mdast-util-to-markdown` escapes a space before a line ending as `&#x20;` (its `unsafe` rule; `sentences.ts:235` already names the case). So the entity is the serializer's correct escape of a trailing space the editor should not be handing it. **Michael's guide's hypothesis (an escaped character at line end makes a strict parser read the next lines as lazy paragraph continuation) is discarded on evidence**: BBEdit 15.5.5 bundles two engines, `Markdown.bblm/Contents/Helpers/cmark` and `Resources/Markdown.pl`; cmark renders `Hello&#x20;` + list as `<p>Hello </p><ul>…` with and without a blank line; Markdown.pl renders the list correctly when a blank line precedes it (entity or not) and collapses it into the paragraph when no blank line precedes it (entity or not, `Hello- a- b`). The entity never changed the outcome; the blank line did. The formatter always writes a blank line between blocks, so Michael's failing file has something this experiment does not reproduce — **the file itself is needed** (Open Questions). Where the fix goes: not a `1.verify` change (it edits product code); a fix task written physically into PRD §8 by the `1.10.r0d` planning commit (on FAIL) or, if the review passes, appended to the Phase 2 plan with the record as its source; the reconciliation decides with the file in hand.
