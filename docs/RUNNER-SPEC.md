# RUNNER-SPEC.md — the orchestration protocol (canonical)

Version: 1.7.0 (2026-09-05; audit #11, resolved by scope cuts, not machinery: publication gates REMOVED from the runner (publication is the manual procedure in `docs/PUBLISH.md`; tasks 6.6h and post.h deleted; no `publication` gateKind); integration, gate-transition and external intents REMOVED (crash safety is `ralph.sh doctor` drift detection plus explicit `admin` commands and a `candidate/<id>` tag written before every ref move); `run.json`/`accepted.json` carry `run_id` and artifact digests; gates never commit (6.2 commits its own `ci-inputs/measure.json`); a workflow-code fix is a `.g<n>` repair, never a same-SHA rerun; one namespace statement. Audit #10: patch phases REMOVED from the runner (post-tag failures halt for a principal decision; no in-runner patch machinery), integration and gate-transition intents for crash safety, generalized verifier grammar and rewiring, 6.2 consumes producer-run artifacts by run id. Audit #9: publication outcomes, pre-review verifier repairs in a `g<n>` namespace, patch phases created by the runner before their planning commit, plan-request failure states, RC packaging on ci refs (no RC tags), successor-branch advance, idempotent re-entry of a completed close, human accepted.json schema, publication CI evidence, plan-request provenance. Audit #8: explicit next-phase metadata, plan requests as first-class state, execution attempts vs graph revisions, accepted-attempt manifests, candidate resolution by verifier, honest candidate/tag relationship, hotfix as a planned phase, versioned close records, attempt-scoped human evidence, `r0` physical ids, conformance tests at bootstrap). Single source of truth for how tasks, branches, reviews, human gates and phases move. PRD §10 summarises it; where the two differ, this file wins. `ralph/` implements it and the Phase 0 review set reviews `ralph/` against it, including its conformance tests (§12). Copied from BUILD-DEFAULTS at bootstrap; itself a reusable default.

Design rule: **phases are strictly sequential, implementation tasks are strictly sequential, and there is exactly one lock.** The only parallelism is the three reviewers of a review set. **The runner ends at `N.close`.** Publishing a tag is a manual procedure (`docs/PUBLISH.md`, summarised in §9) that the runner neither models nor gates; the runner contains **no patch, hotfix or publication machinery** — a broken release is fixed by hand per PUBLISH.md, and a shipped product defect ships its correction in the next phase or in a new project cycle. **Crash safety is detection, not journaling:** the runner writes no intent files; every multi-step mutation leaves a `candidate/<id>` tag before its ref move, `ralph.sh doctor` compares refs, tags, evidence and state and names every inconsistency, and the principal repairs it with an explicit, audited `admin` command (§4.6). The only record written before a ref transaction is the close record (§8).

## 1. State and evidence

**Immutable specification (tracked):** `ralph/tasks.json`, generated from PRD §8 by `ralph/generate-tasks.mjs`. Per task: `id`, `model`, `execution`, `targetBranch`, `sourceBranches?`, `nextPhase?`/`nextBranch?` (close tasks; absent on a terminal close), `releaseVersion?` (release closes), `replanTarget?`, `externalRepoId? externalRepoPath? externalTargetRef? externalVerify?`, `ci?`, `gateKind?`, `outcomes?`, `recordTarget?` xor `recordPolicy: evidence-only`, description, acceptance, dependencies, plus the expansions in §3. **No status field.** It changes only in **planning commits** (bootstrap, reconciliation, resolved plan requests), each followed by `sync-state` (§6).

**Mutable runtime state (host, outside git), written only by `ralph.sh` under the lock (`flock /work/.locks/ralph`), write-temp-then-rename:**
- `state/tasks.json` — per expanded task `{status, outcome?, attempts, task_branch, integrated_sha, accepted_gate_attempt?, started_at, finished_at, notes}`; `status ∈ pending | running | passed | integration-failed | blocked | human-pending | principal-pending | superseded | abandoned`; `outcome ∈ ACCEPT | REJECT | GATE-FAILED` (human). **A dependency is satisfied only by `status == passed` and, for human tasks, `outcome == ACCEPT`.**
- `state/phases.json` — per phase `{phase, branch, base_main_sha, created_by, created_at}`; bootstrap writes Phase 0 from the preflight `main` head; every non-terminal close writes the `nextPhase` record inside its transaction (§8).
- `state/plan-requests.json` — per request `{id, kind: gate-repair, gate, phase, target_branch, trigger_attempt, trigger_outcome, trigger_sha, evidence_path, reason, status ∈ pending | running | blocked | integration-failed | resolved | abandoned, branch, attempts, planning_sha?, created_at, resolved_at?}` (§2); the only request kind in v1 is `gate-repair`; provenance fields are immutable for the life of the request and are quoted in the planning commit message and the audit log.
- `state/audit.log` — append-only record of every transition and command.
- `/logs/state/summary.md` — regenerated after every integration.

**Evidence** (`.evidence/` on the host = `/logs/` in containers; never inside a worktree): `tasks/<id>/<n>.log`; `ci/<id>/a<n>/` per execution attempt: `run.json {run_id, url, sha, workflow, ref, started_at, artifacts: [{name, sha256, bytes}]}` written **first** (as soon as the workflow run id is known; artifacts filled in when fetched), the workflow log, and the artifacts themselves; plus `ci/<id>/accepted.json {attempt, run_id, ref, sha, run_url, workflow, artifacts: [{name, sha256, bytes}], recorded_at}` written atomically on ACCEPT, and `ci/<id>/accepted` → a symlink to the accepted attempt directory; consumers of CI artifacts (6.2, reviewers, §8.3) verify the digests they read against `accepted.json`; `human/<id>/a<n>.md` per execution attempt plus `human/<id>/accepted.json {attempt, evidence_path, outcome, payload, recorded_at}` (payload = the gate's domain fields, e.g. `coachOutcome`, `hunkDecisions`, `baselineDecisions`, `verdictText`); `reviews/<phase>/r<k>/{phase_base_sha, verifier_id, verification_sha, implementation_sha, reconciliation_sha, verdict, claude/, sol/, grok/}`; `closes/<N>.intent.json` and `closes/<N>.json` (§8 schema); `external/<externalRepoId>/state.json`; `publish/<tag>/` (written by hand per `docs/PUBLISH.md`, never read by the runner); `state/`. **Consumers never read a bare `ci/<id>/` or `human/<id>/`; they read through `accepted.json` (or the `accepted` symlink).**

## 2. Execution modes, gate outcomes, plan requests

| mode | runs where | commit? | completes when |
|---|---|---|---|
| `bootstrap` | task 0.0 only; interactively on the host after `docs/PREFLIGHT.md` (host exceptions are exactly: 0.0, human gates via `gate.sh`, host-side scripts, and the authorised Grok fallback below) | yes: the initial commit on `phase/0` | its checks and the conformance tests (§12) pass; `bootstrap.sh` initialises every state file with 0.0 `passed`, the Phase 0 record, and the external-repo state (§7) |
| `loop` | Claude Code in the container, one Ralph iteration per attempt | wip commits on `task/<id>`, one squashed acceptance commit at integration | stop-check passes → integration succeeds |
| `loop-external` | same, in a worktree of the external repo (§7) | one acceptance commit in the external repo | external integration succeeds |
| `reviewer` | one reviewer model, fresh context, read-only snapshot (Grok may run on the host only when its login state cannot be mounted; it then reads a read-only `git worktree` at `implementation_sha` under `/work/.wt/review-grok` and writes only to `.evidence/reviews/<phase>/r<k>/grok/`) | **no** | `/logs/reviews/<phase>/r<k>/<reviewer>/report.md` + `status.json` exist and pass the template check |
| `interactive-principal` | my Opus session on a `task/<id>` branch | one acceptance commit, integrated like `loop` | integration succeeds |
| `replan` | as `loop`; after integration the runner marks `replanTarget` `principal-pending` and emits `REPLAN <replanTarget>` | as `loop` | integration succeeds |
| `human` | Michael on the host via `scripts/gate.sh <id>` | **no** | an attempt record exists, validates, and its outcome is mirrored into state |
| `runner` | `ralph.sh`, deterministic, no model | close: no; `sync-state`: no | its checks pass |

**Human evidence** is evidence-only when produced and attempt-scoped: `gate.sh <id>` writes `human/<id>/a<n>.md` (`n` = execution attempt, from 1) and, on ACCEPT, `human/<id>/accepted.json`. The phase's next reconciliation copies the **accepted** record of every human task of the phase that has a `recordTarget` into `DECISIONS.md` under that section (append mode); `recordPolicy: evidence-only` records (all CI gates) are never copied. Tasks needing a human answer before reconciliation read `/logs/human/<id>/accepted.json`.

**`gateKind` and outcomes** (mirrored into `state/tasks.json`):
- `observation` (1.9, 2.9, 5.3b, 5.3e, 6.4, post.2): outcome `ACCEPT` as soon as the record is complete and validates; domain results live in the payload. → `passed`.
- `approval` (6.3v): `ACCEPT` → `passed`; `REJECT` → `blocked` + plan request.
- `ci` (every generated `<id>h`): `ACCEPT` → `passed` and `accepted.json` written; `GATE-FAILED` → `blocked` + plan request. **A rerun exists only for a transient failure** (runner outage, network, flaky download, cancelled run): `gate.sh rerun <id>h` runs execution attempt `a<n+1>` against the **same SHA and therefore the same workflow file** — a workflow file lives in the tree, so any fix to workflow code changes the SHA and is by definition a `.g<n>` repair through a plan request, never a rerun. GitHub's own "re-run jobs" on an existing run is never used for evidence: every attempt is a fresh run with its own `run_id`.

There is no `publication` gate kind. Publishing is manual (§9, `docs/PUBLISH.md`).

**Gate transitions and crashes (no intents).** `gate.sh <id>` proceeds, under the lock, in this fixed order: (1) `ci/<id>/a<n>/run.json` (or `human/<id>/a<n>.md`) — the attempt now exists on disk with its remote identity (`run_id`, `ref`) before any remote wait; (2) on completion, the attempt's evidence and, on ACCEPT, `accepted.json` + the `accepted` symlink; (3) the task's `outcome` and `status`; (4) exactly one plan request when the outcome demands one, with the id `plan.<gate>.r<n>` computed from the count of existing requests for that gate. A crash between steps leaves the attempt directory as the record of what happened: `ralph.sh doctor` reports an attempt whose `run.json` has no matching state transition as `incomplete <id> a<n>`; the principal finishes it with `gate.sh <id> --resume a<n>`, which re-reads the named run by `run_id` (never starts a new one), re-fetches artifacts if their digests are missing, and continues from the first step whose artefact is absent. Nothing is ever rolled back or discarded: an attempt with remote side effects (a pushed ci ref, a workflow run) is either resumed or explicitly abandoned with `gate.sh abandon <id> a<n> --reason`, which writes `a<n>/abandoned.json` and leaves the directory. Orphan `ci/<id>/a<n>` refs on the remote are harmless (immutable, never a trigger source after the run) and are deleted by `gate.sh gc`, which lists them and deletes only refs whose attempt directory is `accepted`, `rejected` or `abandoned`.

**Attempt and revision namespaces (the only three).** `a<n>` — an execution attempt of the *same* task against the *same* SHA (CI reruns, human gate retries); it never changes the graph. `.g<n>` — a repair of a `needsCI` producer after a code-caused CI failure (§2 rewrite rule (a)); it is a new task with a new SHA. `.r<n>` — a revision of a review attempt or an approval gate (review sets `<id>.r<k>`, verifiers `N.verify.r<k>`, approval retries `<A>.r<n>`, plan requests `plan.<gate>.r<n>`); also new tasks. A gate's id never changes across `a<n>` reruns; every `.g<n>`/`.r<n>` id is a different task that replaces the old one in its dependents.

**Plan requests** (the only way a rejected or failed gate re-enters the graph). When a gate transitions to `blocked` with a plan outcome, `ralph.sh` appends a request `plan.<gate>.r<n>` (`n` increments per gate) with the §1 provenance fields and emits `PLAN-GATE <request-id>`. **Transition table** (all under the lock, all audited):
| from | command / event | to |
|---|---|---|
| `pending` | `ralph.sh plan <id>` | `running`: branch `plan/<gate>/r<n>` + worktree created from the request's `target_branch` head |
| `running` | I commit `wip(plan.<gate>.r<n>): …` freely and emit `<promise>DONE <request-id></promise>` when the planning change is complete (generic §4 lifecycle; the squashed candidate is `plan(<request-id>): …`) | integration transaction |
| `running` | rebase conflict, or 3 failed attempts | `blocked` |
| `running` | detached-test failure of the planning candidate | `integration-failed` |
| `blocked` / `integration-failed` | `ralph.sh plan-retry <id>` (branch kept, `attempts = 0`) | `pending` |
| `blocked` / `integration-failed` / `pending` | `ralph.sh plan-abandon <id> --reason` (branch kept as `abandoned/plan/<gate>/r<n>`, the gate stays `blocked`) | `abandoned` |
| integration transaction succeeds | `planning_sha` recorded, `sync-state` runs, the originally blocked gate → `superseded`, dependents already rewired by the commit | `resolved` |

**Rewrite rules for the planning commit**: (a) code-failed CI gate `<X>h`: append fix tasks after `<X>` and a replacement producer in the **gate-repair namespace** `<X>.g<n>` (`needsCI`, same `ci` object with `refTemplate` re-derived), whose generated `<X>.g<n>h` gate replaces `<X>h` in every dependent; when `<X>` is a verifier of any review attempt, **whichever not-yet-started review attempt depended on `<X>h` is rewired** to `<X>.g<n>h`, and that attempt's `verifier_id` is recorded from its actual accepted dependency at review start. Verifier ids follow the grammar `N.verify[.r<k>][.g<n>]`: `.r<k>` = the review attempt the verifier belongs to (absent for `r0`), `.g<n>` = the n-th repair of that verifier. (b) rejected approval gate `<A>`: append fix/measurement tasks and a new approval task `<A>.r<n>` (same `gateKind`, `recordTarget`, `outcomes`) that replaces `<A>` in every dependent. RC packaging gates are `ci`-ref gates (§3), so rule (a) covers them; **no tag other than the final release tag is ever created**.

## 3. Generator expansions (validated by `ralph/validate-tasks.mjs`)

- **Review sets.** `model: review-set` on `<id>` generates physical ids `<id>.r0a`, `<id>.r0b`, `<id>.r0c` (`reviewer`: Claude, Sol, Grok; depending on `<id>`'s dependencies) and `<id>.r0d` (`interactive-principal`, reconciliation; depending on all three). Dependents of `<id>` → `<id>.r0d`. The phase's initial verifier is `N.verify`; each attempt's actual verifier is whatever `N.verify[.r<k>][.g<n>]` its review tasks depend on when they start, and `verifier_id` records it. A reconciliation with verdict FAIL on attempt `r<k>` appends, in its planning commit: fix tasks; `N.verify.r<k+1>` (`needsCI`, depending on the last fix task); `<id>.r<k+1>a/b/c/d` (depending on `N.verify.r<k+1>h`); dependents rewired to `<id>.r<k+1>d`. The validator requires one `r0` review set and one `r0` verifier per phase, one verifier + gate per attempt, a linear attempt chain, and that `N.close` depends on the newest attempt's `d`.
- **CI gates.** `needsCI: true` on `<id>` → `<id>h` with `execution: human`, `blockedOnHuman: true`, `gateKind: ci`, `outcomes: {ACCEPT: continue, GATE-FAILED: plan-gate}`, `recordPolicy: evidence-only`; dependents of `<id>` → `<id>h`; `ciAcceptance` becomes `<id>h`'s acceptance. `<id>.ci` = `{refType: ci|tag, refTemplate, workflow, trigger, artifactNames[], cleanupRef}`; for `ci`, `refTemplate` is `ci/<id>/a{n}` (`n` = execution attempt), the gate pushes `integrated_sha` of `<id>` to that immutable ref, writes `run.json` as soon as the run id is known, waits for the named workflow, fetches artifacts into `ci/<id>h/a<n>/` (evidence is keyed by the **gate id**, DECISIONS #018) and records their digests, on ACCEPT writes `accepted.json` and the `accepted` symlink, and finally deletes the ref (§2 order). **Gates never commit.** Every input a workflow needs beyond the tree at `integrated_sha` is committed by the producer task itself (6.2 commits `ci-inputs/measure.json` naming the rc1 producer `run_id` and artifact digests read from `/logs/ci/6.1/accepted.json`), so `integrated_sha == the SHA CI ran` holds for every gate without exception. For `tag`, `refTemplate` is the literal tag, created annotated on `integrated_sha` with expected-old = zero OID.
- `targetBranch` is derived unless given (`0.*…4.*, 6.*` → `phase/N`; `5.*`, `post.*` → `phase/5`); `N.close` → `sourceBranches: [phase/N]`, `targetBranch: main`.
- **RC packaging** uses `refType: ci` with `release-candidate.yml` (installers uploaded as artifacts from the immutable ci ref); Michael installs release candidates from `ci/<id>/accepted/`. `refType: tag` exists only for documentation of the final tag, which is created by `N.close`, never by a gate.
- Validator asserts: unique expanded ids; dependencies resolve; acyclic; `execution` ∈ `bootstrap | loop | loop-external | reviewer | interactive-principal | replan | human | runner`; `blockedOnHuman` only on `human`; `human` ⇒ `gateKind`, (`recordTarget` xor `recordPolicy`), and `outcomes` for `approval`/`ci` (the validator's fixtures include an approval task without `outcomes` and a task with an unknown `gateKind` such as `publication`, and assert rejection of both); `needsCI` ⇒ `ci` with `refType: ci ⇒ cleanupRef: true`; `replan` ⇒ `replanTarget` resolves to `interactive-principal`; `loop-external` ⇒ all four external fields; every close ⇒ one `sourceBranches` entry, `targetBranch: main`, and either both `nextPhase`+`nextBranch` or neither (terminal); release closes ⇒ `releaseVersion`; every phase has exactly one `r0` review set, one initial verifier (`N.verify`, repairs in `g<n>`) and one close; no `ci` object with `refType: tag` on any `needsCI` task; expanded count equals `ralph/EXPECTED_COUNT`.

## 4. Task lifecycle (`loop`, `interactive-principal`, `replan`, planning commits)

1. **Start** (under the lock): read `targetBranch` head; create `task/<id>` (or `plan/<gate>/r<n>`) and its worktree; state `running`.
2. **Iteration**: `git status` → a dirty tree is committed first as `wip(<id>): recovery` (no rebase here; the only rebase is at integration); orient (CLAUDE.md → `/logs/state/summary.md` → the task's entry in `ralph/tasks.json` → `docs/lessons.md` → any `/logs/human/<id>/accepted.json` the task names); implement; verify; append a journal entry to `docs/progress/journal-main.md` (no commit SHA); commit `wip(<id>): …`; emit `<promise>DONE <id></promise>` only if acceptance is met; stop. Transcript → `/logs/tasks/<id>/<n>.log`.
3. **Stop-check**: journal entry present for this attempt; a wip commit exists; from 0.1 onward `pnpm lint && pnpm test && cargo test` green on the branch. `DONE` + green → integrate. Otherwise `attempts += 1`; at 3 → `blocked`, `STUCK <id>`.
4. **Integration transaction** (under the lock; the only way a target branch moves): `expected_old = rev-parse targetBranch` → rebase the branch onto it (conflict → `blocked`, `CONFLICT <id>`) → build the squashed candidate (`task(<id>): …` or `plan(<request-id>): …`, acceptance text + `Depends-on:` closure) with `commit-tree`, without moving the branch → run the full suite on the candidate in a detached worktree (failure → tag `wip/<id>-<attempts>`, `integration-failed`, `INTEGRATION-FAILED <id>`) → tag `candidate/<id>` on the candidate (force-updated; the candidate's message carries `Expected-old: <expected_old>`) → `git update-ref refs/heads/<targetBranch> <candidate> <expected_old>` → state `passed`, `integrated_sha`; regenerate summary; tag `wip/<id>`; remove worktree and branch; `replan` tasks then set `replanTarget` `principal-pending` and emit `REPLAN`; planning commits then run `sync-state`. The same sequence applies to planning commits and to external integrations (§7).
5. **Recovery commands** (under the lock, audited): `retry <id>` (`blocked`/`integration-failed` → `pending`, branch kept, `attempts = 0`); `resume <id>` (`blocked` after a manual fix → `running`); `resolve-conflict <id>`; `abandon <id> --reason` (`abandoned`, branch kept as `abandoned/<id>`; dependents stay blocked until a planning commit replaces it); `plan <request-id>`, `plan-retry`, `plan-abandon` (§2); `rerun <id>h` (§2). A new candidate supersedes earlier `wip/<id>-n` tags.
6. **Crashes and drift (no intents in v1).** A crash between the ref move and the state write cannot lose work: the candidate is reachable from `candidate/<id>` and the target branch either equals it or `expected_old`. `ralph.sh run` refuses to start while `ralph.sh doctor` reports anything; `doctor` (read-only, no lock needed) checks, for every task: `running` with no worktree; `candidate/<id>` present while state is not `passed` (reports `unfinished-integration <id>` with whether the target ref equals the candidate, the expected-old, or neither); `passed` while `integrated_sha` is not an ancestor of the target branch; CI or human attempt directories with no matching state transition (`incomplete`, §2); a plan request `running` with no branch; external-repo drift from `external/<id>/state.json`; close records whose refs drifted. Each report line names the one `admin` command that fixes it. `admin` commands (under the lock, audited with the doctor line quoted): `admin mark-integrated <id>` (allowed only when the target ref equals `candidate/<id>`: completes the post-ref steps exactly as the transaction would have); `admin retry <id>` (allowed only when the target ref equals `expected_old`: deletes `candidate/<id>` and re-queues the task from the rebase); `admin resolve-request <request-id> --state <s>`; anything else → the principal records a manual repair in `DECISIONS.md#repair-<id>` and runs `admin mark-integrated` or `admin retry` afterwards. The runner never guesses.

## 5. Reviews

1. When all dependencies of attempt `r<k>` are `passed`, `ralph.sh` records in `/logs/reviews/<phase>/r<k>/`: `phase_base_sha`, `verifier_id` (the actual accepted verifier gate's producer, grammar `N.verify[.r<k>][.g<n>]`, read from the attempt's dependency at start), `verification_sha` (that verifier's `integrated_sha`), `implementation_sha` (`targetBranch` head). Gates produce no commits and the verifier is the last commit-producing task before the attempt, so `verification_sha == implementation_sha` is asserted; the review does not start otherwise.
2. The three reviewers run in parallel: each a worktree at `implementation_sha` mounted read-only, `/logs` read-only, own report directory writable. Claude and Sol also get `/scratch/<reviewer>`, a local clone of `/work` at `implementation_sha`, for the fresh cold build and test run; it must be clean at exit and is deleted. Grok reads the tree and `/logs` only and cites `/logs/ci/<verifier_id>h/accepted/` (the gate id, DECISIONS #018) for the cold build. Reviewers cannot see one another's directories.
3. Inputs: `docs/PRD.md`, `docs/RUNNER-SPEC.md`, `docs/lessons.md`, `git diff <phase_base_sha>...<implementation_sha>`, `/logs/ci/<verifier_id>h/accepted/` (gate id) and the phase's other `/logs/ci/*h/accepted/`, `/logs/tasks/*`, `/logs/human/*/accepted.json`, the gate row. Output per `docs/reviews/TEMPLATE.md`.
4. **Reconciliation** (`<id>.r<k>d`, one planning commit): copy the three reports to `docs/reviews/phase-N-r<k>-{claude,sol,grok}.md`; append the accepted record of every human task of the phase with a `recordTarget` into `DECISIONS.md` under it (never `evidence-only` records); write `DECISIONS.md#review-N-r<k>` (verdict per criterion, findings with severity and disposition); append class-level lessons; regenerate `docs/progress.md`; for a release phase finalise that phase's release notes (`RELEASE-NOTES-v0.1.0.md` for Phase 6, `RELEASE-NOTES-v0.2.0.md` for Phase 5) with the phase's dispositions and the complete backlog. Write `verdict: PASS | FAIL` to the attempt directory and the DECISIONS entry. **Severity rule**: any `blocker`, or `should-fix` marked required → FAIL with the §3 attempt expansion in the same commit; `nit`/deferred → `docs/V1.1-BACKLOG.md`. The reconciliation task reaches `passed` when its planning commit integrates regardless of verdict; `N.close` requires the newest attempt's verdict PASS. The commit's SHA is `reconciliation_sha`; `sync-state` follows.
5. `promote-lessons` is a manual step, not a script (DECISIONS #review-0-r0, Grok finding 4): the reconciliation of attempt `r<k>` names the lessons to promote, verbatim, in the text of the next verifier task (`N.verify.r<k+1>`, or the next phase's `N+1.verify` after a PASS), and that verifier task applies them to `CLAUDE.md`/`AGENTS.md`, so the changes are part of the verified, reviewed code.

## 6. `sync-state` (runner, under the lock, after every planning commit)

Regenerate `tasks.json` from PRD §8 and assert byte-identity with the committed file; add new tasks to runtime state as `pending`; keep every existing record; reject deletion or mutation of any task that has left `pending` (except the `superseded` transition made by a resolved plan request); recompute dependency edges; write the state file atomically; append to the audit log.

## 7. `loop-external` transaction

Bootstrap validates the external checkout at `externalRepoPath` is clean, that `externalTargetRef` and `externalVerify` exist and the verifier passes, and writes `external/<externalRepoId>/state.json {target_ref, base_sha}`. Under the lock, a `loop-external` task reads that base SHA; creates `task/<id>` worktree in the external repo; iterates there (journal to `/logs/external/<externalRepoId>/journal.md`); stop-check runs `externalVerify`; integration = rebase → squash → `externalVerify` in a detached worktree → tag `candidate/<id>` in the external repo → `update-ref <externalTargetRef> <candidate> <expected_old>` → record `integrated_sha` in external state → remove the worktree (`doctor`/`admin` rules as in §4.6, applied to the external repo). No Essay Down commit; the phase reconciliation records the external SHA in `DECISIONS.md`.

## 8. Phase close (`N.close`, `runner`, under the lock, transactional and idempotent)

0. **Re-entry**: if `closes/<N>.json` already exists, validate its schema, confirm every `refs[].ref` still equals `intended_oid`, and return success without mutation; on any drift fail loudly (`CLOSE-DRIFT <N>`). If `closes/<N>.intent.json` exists, resume at step 5's retry rule.
1. **Preconditions** (nothing moves): `sourceBranches[0]` head == `reconciliation_sha` of the newest attempt, whose `verdict == PASS`; `git diff --name-only implementation_sha reconciliation_sha` ⊆ `{docs/**, DECISIONS.md, ralph/tasks.json, ralph/EXPECTED_COUNT}`; `main` head == `phases.json[<this phase>].base_main_sha` (fast-forward-only).
2. **Candidate**: the proposed `main` commit is `reconciliation_sha`; run the full suite on it in a detached worktree.
3. **Release checks** (release closes): every version field equals `releaseVersion`; the **approved product candidate** is resolved as the accepted attempt of the newest passing attempt's verifier gate (`<verifier_id>h`, read through its `accepted.json`) and its `sha` must **equal** that attempt's `verification_sha`, which is an ancestor of the proposed commit differing only by the §8.1 allowlist. Honest statement of what this proves: the installers were built from the exact product tree that is being tagged; the tagged commit adds only review documents. The manual publication procedure (§9) checks the packages rebuilt by `release.yml` from the tagged commit against the same digests. Create the annotated tag object `v<releaseVersion>` on the proposed commit.
4. **Intent**: write and fsync `closes/<N>.intent.json` (schema below).
5. **Ref transaction**: one `git update-ref --stdin` transaction with every entry from the intent's `refs[]`: `refs/heads/main` (expected-old = `base_main_sha`), `refs/tags/v<releaseVersion>` (expected-old = zero OID, intended = the tag object OID) when applicable, `refs/heads/<nextBranch>` (expected-old = zero OID, intended = the proposed commit) when `nextPhase` is set. On any failure nothing moves.
6. **Finalise**: when `nextPhase` is set, write `phases.json[nextPhase] = {phase: nextPhase, branch: nextBranch, base_main_sha: main_sha, created_by: <this close id>, created_at}`; a terminal close writes no phase record; rename the intent to `closes/<N>.json`. **Retry** after a crash: if the intent exists and every `refs[].ref` already equals its `intended_oid`, skip to finalise; if none moved, re-run from step 1; a partial state is impossible because step 5 is atomic.

**Close record schema (v1)**: `{schema: 1, close_id, phase, review_attempt, verifier_id, verification_sha, implementation_sha, reconciliation_sha, base_main_sha, main_sha, release_version?, candidate_gate_id?, candidate_attempt?, candidate_sha?, tag?: {name, tag_object_oid, tag_target_sha}, next_phase?, next_branch?, refs: [{ref, expected_old_oid, intended_oid}], written_at}`. The intent and the final record are the same document.

## 9. Branch topology and publication

`phase/0 → 1 → 2 → 3 → 4 → 6` (`4.close`: `nextPhase 6`), each fast-forwarding into `main`; `6.close` (`nextPhase 5`, `releaseVersion 0.1.0`) tags `v0.1.0` and creates `phase/5`; Phase 5 starts at `6.close` (its `5.0` depends on `6.close`); `5.close` (terminal, `releaseVersion 0.2.0`) tags `v0.2.0`. `main` never moves except at a close.

**Publication is manual and outside the runner** (`docs/PUBLISH.md`). After a release close Michael, by hand: reads `closes/<N>.json`; pushes `main` and the tag; watches `release.yml` run on the tag; checks the publication invariant himself — run SHA == tag target SHA == `main_sha`, artifact names and checksums carry `releaseVersion`, and each artifact's `sha256` equals the digest in `/logs/ci/<candidate_gate_id>/accepted.json` (a mismatch means the release build is not reproducible and is investigated before the release is marked public); records the run id, URL and outcome in `.evidence/publish/<tag>/publish.md` and in `DECISIONS.md#publish-<tag>`. Nothing in `state/` changes; the graph has no publication task; Phase 5 proceeds regardless. Consequences, stated plainly: a `v0.1.0` tag can exist on `main` and on the remote while its GitHub release is missing or broken. Only a transient failure (runner outage, upload error) is retried against the same tag, as a fresh workflow run recorded in `publish.md`; a broken `release.yml` cannot be fixed for a tag that already exists, because the workflow file is part of the tagged tree — the fix lands in the next phase and the release notes for the tag say so. Tags are never repointed or deleted. Shipped product defects are corrected in the next phase or in a new project cycle planned like Phase 0; the v1 runner has no patch machinery by design. **v1.1 runner backlog:** automated publication verification (`ralph.sh publish-check <tag>`) reading `publish.md` and the release API, once the manual procedure has run at least twice.

**Retrospective cutoff.** post.1–post.4 run before Phase 5's own review; the 5.4 reconciliation writes that review's class-level lessons to `docs/RETRO-CARRYFORWARD.md`, applied at the next project's BUILD-DEFAULTS step 0.

## 10. Summaries, journals, lessons

`/logs/state/summary.md` (outside git): ≤ 6-line current state + last 5 journal entries + open gates and plan requests, regenerated after every integration. `docs/progress.md` (tracked): regenerated only in reconciliation commits. One journal, `docs/progress/journal-main.md`: append-only, never pruned, never carries its own commit SHA. `docs/lessons.md` is append-only with `merge=union`; nothing else is union-merged.

## 11. Loop parameters, stop signals, entry points

`--max-turns 50` (implementation) / 30 (setup); 15 iterations per run; watch the first 3 transcripts in `/logs/tasks/`. Stop signals: `STUCK`, `CONFLICT`, `INTEGRATION-FAILED`, `HUMAN_GATE <id>`, `PRINCIPAL <id>`, `REPLAN <id>`, `PLAN-GATE <request-id>`, `DOCTOR <n> findings` (run refused until clean), `CLOSE-DRIFT <N>`, `<promise>COMPLETE</promise>` (all tasks of the phase passed), a missing journal entry, or no wip commit in two iterations. `HUMAN_GATE N.verifyh` is followed by the advisory line `ROTATE-PRINCIPAL` (not a stop signal), which `scripts/gate.sh` repeats after recording any `N.verifyh` attempt: the principal session rotates there (PRINCIPAL.md, DECISIONS #015). Entry points (this list is the one task 0.0 implements, byte for byte): `ralph/bootstrap.sh`; `ralph.sh run [--phase N] | retry <id> | resume <id> | resolve-conflict <id> | abandon <id> --reason <text> | plan <request-id> | plan-retry <request-id> | plan-abandon <request-id> --reason <text> | rerun <gate-id> | close <N> | sync-state | status | doctor | admin mark-integrated <id> | admin retry <id> | admin resolve-request <request-id> --state <s>`; `docker compose run claude-task <id> | claude-review | codex-review | grok-review <phase> <attempt>`; `scripts/gate.sh <id> [--resume a<n>] | rerun <gate-id> | abandon <id> a<n> --reason <text> | gc` (host); `scripts/fetch-ci-logs.sh` (host).

## 12. Conformance tests (part of bootstrap; the Phase 0 review's first target)

`ralph/test/` runs against disposable fixture repositories and must pass before `bootstrap.sh` initialises state: integration transaction (candidate built without moving the branch; CAS mismatch restarts; detached-test failure leaves the branch untouched); approval rejection → plan request → planning commit → dependents rewired → superseded gate; code-failed CI gate → replacement verifier and gate; transient rerun (`a2` against the same SHA, `accepted.json` points at `a2`); failed review `r0` → `N.verify.r1` + `r1` review set → close depends on `r1d` and resolves the candidate from `N.verify.r1h`; crash injected before and after the close ref transaction (retry is a no-op or a clean re-run, never partial); phase records for the `4 → 6 → 5 → terminal` order; initial verifier CI failure → `N.verify.g1` repair → `r0` review fails → `r1` review → `N.verify.r1` CI fails → `N.verify.r1.g1` repair → `r1` review rewired (no id collision, `verifier_id` correct at each step); a completed close re-entered (no-op) and re-entered after ref drift (loud failure); crash injected after the `candidate/<id>` tag but before `update-ref`, and after `update-ref` but before the state write, for a task, a planning commit and an external task (`doctor` reports exactly one finding naming the right `admin` command; `run` refuses; `admin retry` / `admin mark-integrated` restore a clean `doctor`; the wrong `admin` command is refused); crash injected after a CI attempt's `run.json` but before the state transition (`doctor` reports `incomplete`, `gate.sh --resume a<n>` completes it without a new workflow run, `run_id` unchanged); `gate.sh gc` deleting only refs of `accepted`/`rejected`/`abandoned` attempts; a gate `accepted.json` whose artifact digests disagree with the files on disk is rejected by every consumer (6.2 fixture, §8.3); a rerun requested after a workflow-file change is refused (`SHA changed: use a .g<n> repair`); the validator rejecting `gateKind: publication`; a planning candidate failing its detached test → `integration-failed` → `plan-retry`; `sync-state` refusing mutation of a started task; validator rejecting each schema violation listed in §3.
