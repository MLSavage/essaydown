## #012-container-credentials (2026-09-05, task 0.0; principal, verified on the Mini)

- PREFLIGHT §0.5 assumed the host's `~/.claude`, `~/.codex` and `~/.grok` could be bind-mounted read-only into the container. Verified false for Claude Code on macOS: its login lives in the macOS Keychain, not in `~/.claude`, and the CLI writes to its config dir on every run. Grok's `~/.grok` also holds its binary and caches next to `auth.json`.
- Cut, not machinery: each CLI logs in **once inside the container** (`docker compose run --rm claude-login | codex-login | grok-login`, subscription accounts, no API keys) and its state persists in a container-owned named volume (`essaydown-claude-home`, `essaydown-codex-home`, `essaydown-grok-home`) mounted as that CLI's home directory. Nothing from the host's `~/.ssh`, `~/.config/gh`, `~/.claude`, `~/.codex` or `~/.grok` is ever mounted; `boundary-check` proves the git/gh side of the boundary and its output is quoted in the 0.0 journal entry. The 0.0 acceptance phrase "credentials mounted read-only" is therefore satisfied in spirit (the host's login state is never exposed) and not literally (the container's own login state is writable, because the CLIs rotate tokens).
- Reversal: `docker volume rm essaydown-claude-home essaydown-codex-home essaydown-grok-home` and log in again.

- **Cause (principal reading; the fix task confirms it from the log before changing anything).** The three tests read the OS clipboard back through `navigator.clipboard.readText()` after `copyMarkdown` (`apps/desktop/src/dev/DevEditor.tsx`) wrote it with `navigator.clipboard.writeText(text)`. On Windows, Chromium hands plain text to the system clipboard with LF converted to CRLF, so the read returns the word, a carriage return and a newline where the assertion expects the newline alone. The app wrote the right bytes (`format(root)` ends in `\n`, the same string the Linux and macOS legs read back); the assertion encoded one platform's clipboard convention — the same class as #018 (CRLF at checkout) and #020 (a `Mod-` chord resolved from the host platform): green in the container and on two runners by accident of platform. The spec's own doc comment (task 1.14) already states why a copy case should not go through the OS clipboard: it is one shared resource across parallel workers on three OSes; 1.23's three cases are the only copy cases in the tree that do. Code-caused (test code), not transient: no `gate.sh rerun`; any tree change is a `.g<n>` repair (RUNNER-SPEC §2).
- **Scope decision (explicit, so the fix task does not pick).** Three candidates: (1) normalise the carriage return away in the assertion; (2) branch the expected value on `process.platform`; (3) spy `navigator.clipboard.writeText` before the page's scripts run (`page.addInitScript`) and assert the string the app handed the clipboard API, byte-exact. Chosen: (3). It is strictly better, not a compromise: it asserts the app's own output on every OS with no normalisation (1 would hide a stray carriage return the app might one day write), encodes no platform list (2, forbidden by the [plan.1.verifyh.r0] lesson and the next-prompt rule), keeps the real code path under test (flush → format → writeText → the `"Copied Markdown"` status), removes the shared-OS-clipboard hazard the spec's doc comment names, and drops the `clipboard-read` permission grant those three tests no longer need. The foreign-paste case keeps the real clipboard: pasting content from outside the editor is exactly the case where the source has to be outside the editor. G1's guard stays live: the task re-runs 1.23's flush-removal mutation against the spy and records that the presence case alone turns red.
