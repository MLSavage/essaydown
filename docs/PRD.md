## 1. Problem

Michael writes in Markdown and loves Typora's rendered-by-default simplicity, but Typora has no concept of the essay as a structure of questions, blocks, and sentences. The Essay app (essay.app, Julian Peterson) has that structure — Outline, Produce, Rewrite, Reorder — but stores documents in its own cloud, exports only to PDF/DOCX/Google Docs, and does not speak Markdown.

Essay Down is one application that does both: a bare-bones Typora-class Markdown editor whose document is also a tree of blocks and sentences, with the four Essay modes as different views over the same plain `.md` file. It replaces Typora for daily writing and replaces the Essay app for structured drafting. Nothing is hosted; the document is a file.

## 2. User

One primary user (Michael), technically fluent, writing essays, articles, and client documents. Primary machine is an M5 Max MacBook Pro; also a Mac Mini, a planned Omarchy (Arch) Linux machine, and a Windows machine used by his son. Documents live in a folder he already syncs (iCloud Drive / Syncthing / git). He must be able to open the same `.md` in Typora, Obsidian, or `cat` and see clean Markdown.

## 3. The one workflow

1. Open a folder. Create `my-essay.md`.
2. **Outline**: type the topic question, then the supporting questions, nest and drag them into order. Each question becomes a heading.
3. **Produce**: distraction-free writing under each heading; the heading's question hovers faintly above it.
4. **Rewrite**: sidebar lists every sentence of the current paragraph; write alternative versions of a sentence; click the winner; it replaces the original in the document.
5. **Reorder**: drag sentences within a paragraph, paragraphs within a section, sections within the essay.
6. Toggle to source view to see the raw, color-coded Markdown; toggle back.
7. Export to DOCX / PDF / HTML / EPUB.
8. (AI build only) Ask the coach about a sentence or paragraph; it replies with questions, never with text to paste.

If steps 1–7 work end to end on all three OSes, v1 is done. Step 8 is wanted but not release-blocking: v0.1.0 ships at `6.close` without the coach; Phase 5 (coach + retrospective) runs after it, strictly sequentially, and ships as v0.2.0 (RUNNER-SPEC §9). Steps 1–7 are encoded once as `e2e/one-workflow` (task 3.6) and reused by every later gate.

## 5. Non-goals (v1)

- **No** math / LaTeX / KaTeX. **No** Mermaid or any diagrams. **No** footnotes, task lists, emoji shortcodes, TOC macros, front-matter editors beyond `title`/`question`.
- **No** themes or theme switcher. One light theme, one dark theme following the OS.
- **No** cloud, accounts, sync, or telemetry. The app makes zero network calls while `coach.provider === null`. With the `openai-compatible` provider it talks only to the configured base URL; with the `claude-cli` provider the network traffic is the Claude Code CLI's own (to Anthropic), outside the app's control and documented as such.
- **No** AI rewriting. The hard guarantee, enforced in code, is that **nothing a model produces is ever inserted into the document**; the only path into the text is the user typing. The question-only filter (task 5.3a) is best-effort on top of that: it catches obvious paraphrases-as-questions, not every semantic rewrite. If a provider/model fails the evaluation in 5.3b, that provider is disabled in settings and v1 can ship with the coach disabled entirely.
- **No** citation / reference manager, Zotero, Notes module, Topic Explorer.
- **No** plugin system, multi-window, or tabs (one document open at a time; the file tree switches).
- **No** dragging a sentence out of its paragraph into another paragraph (v1.1 candidate).
- **No** whole-essay coach (v1.1 candidate).
- **No** code signing / notarization in v1.
- **No** mobile.
- Agents do **not** add features not listed in a task.

### 6.1 Document model

- **Source of truth in memory**: an `mdast` root produced by `remark-parse` with the extensions in §4, restricted to: `root, heading (1–6), paragraph, text, emphasis, strong, inlineCode, delete, link, image, list, listItem, blockquote, code (fenced), thematicBreak, table/tableRow/tableCell, break, html, yaml`.
- **Opaque set** = `html` nodes, and `yaml` front matter **except the two app-owned keys** `title` and `question`. `html` is rendered as a grey read-only box and is byte-identical after every round-trip. `yaml` is hidden in the rendered view and byte-identical after round-trip *unless* the user changed `title` or `question` in-app (Outline mode); then only those two lines are rewritten in place and every other byte of the block is preserved. **Supported boundary**: an app-owned key is rewritable only when it is a unique top-level key whose value is a single-line plain, single-quoted or double-quoted scalar, optionally followed by an inline ` # comment` (quoting style and comment are preserved). Block scalars (`|`, `>`), flow syntax, multi-line continuations, duplicate keys, or malformed front matter make the key **read-only**: Outline shows the value greyed with 'Edit this in the source view', and an attempted write returns `FrontMatterUnsupported` instead of rewriting anything. Invariant C therefore excludes yaml only on saves where an app-owned key changed, and a test pins that a save with an unchanged topic question leaves the block byte-identical. The sidecar mirrors the two keys and wins on conflict (§6.2), but it writes to front matter only on such an in-app edit, never on open. Any syntax the parser does not recognise (e.g. `[^1]`) is plain `text`; it is preserved *semantically* (invariant B) but may be re-escaped by the formatter, and that is accepted.
- **Block** = any direct child of `root`, plus each `listItem` and each `tableRow`. Blocks carry a **contentId** = `fnv1a64(normalizedText)` as 13-char base-36 `+ '-' + occurrence` (0-based ordinal among blocks with the same hash, in document order), recomputed on every parse. ContentIds are never written into the Markdown and change whenever the block's text changes; they exist for anchoring (§6.2), not for cursor tracking (the store tracks the cursor by ProseMirror position).
- **Sentence** = segment of a `paragraph` block's plain text from `Intl.Segmenter` (or the fallback), post-processed so `e.g.`, `i.e.`, `Dr.`, `Mr.`, `Mrs.`, `Ms.`, `vs.`, `etc.`, single capital letters followed by a period, and decimal numbers do not split. Each sentence carries `{blockId, index, start, end, text}`; inline marks are preserved on replacement by mapping offsets back through the mdast inline children.
- **Rewrite/Reorder scope (v1)**: sentences are addressed only in **top-level** paragraphs (direct children of `root`). Paragraphs nested inside list items or blockquotes appear in the Rewrite/Reorder sidebars as read-only cards labelled "nested — edit in the document"; they have no `blockId` for sentence operations. Lifting this is a v1.1 candidate.
- **Replacement semantics**: `replaceSentence` takes inline Markdown text; the replaced range (including any marks inside it) is replaced wholesale by the parsed inline content of the new text, and marks that begin or end outside the range survive untouched. So replacing 'A **bold** start.' with 'A quiet start.' yields plain text, and with 'A **quiet** start.' yields bold again — the user controls marks by writing Markdown.
- **Section** = a heading and every block up to the next heading of equal or shallower depth.
- **Topic question** lives in front matter (`question:`) and the sidecar; it is **never** materialised as an H1. Supporting questions become H2/H3/… headings.
- **Canonical formatter** (`core/format.ts`): `remark-stringify` per `docs/MARKDOWN-STYLE.md`. Invariant A (idempotence): `format(parse(format(x))) === format(x)`. Invariant B (semantic preservation): `parse(format(x))` deep-equals `parse(x)` with positions stripped. Invariant C (byte fidelity): if `x` is canonical, `format(parse(x)) === x`; and the opaque set is byte-identical in every case.
- **Save policy**: written in canonical form on every save. First open of a non-canonical file shows a one-line banner ("This file will be saved in Essay Down's Markdown style") with an Undo-open option.

### 6.2 Sidecar (`<name>.essaydown.json`)

```json
{
  "version": 1,
  "topicQuestion": "What should wrap the editor?",
  "headings": [ { "anchor": { "kind": "heading", "hash": "0a1b2c3d4e5f6", "occurrence": 0, "text": "Tauri is the right shell", "depth": 2, "sectionHash": null }, "question": "What should wrap the editor?" } ],
  "rewrites": [ { "anchor": { "kind": "sentence", "hash": "…", "occurrence": 0, "text": "<original sentence>", "sectionHash": "<hash of enclosing heading>", "blockHash": "<hash of enclosing paragraph>" }, "variants": [ { "text": "…", "createdAt": "…" } ], "chosen": 1, "history": [ { "text": "…", "replacedAt": "…" } ] } ],
  "coach": [ { "anchor": { "kind": "sentence", "hash": "…", "occurrence": 0, "text": "…", "sectionHash": "…", "blockHash": "…", "pos": [4, 1] }, "scope": "sentence", "question": "…", "askedAt": "…" }, { "anchor": { "kind": "paragraph", "hash": "…", "occurrence": 0, "text": "…", "sectionHash": "…", "pos": [4] }, "scope": "paragraph", "question": "…", "askedAt": "…" } ],
  "orphans": []
}
```

- **Anchoring** is deterministic, scoped, and honest about its limits. An anchor is `{kind, hash, occurrence, text, sectionHash, blockHash?, pos}` where `pos` is the item's last known document position (top-level block index, plus sentence index for sentences), refreshed on every save. Resolution order on load: (1) exact `hash` + `occurrence` within the same `sectionHash` (or `blockHash` for sentences); (2) exact `hash` + `occurrence` anywhere; (3) exact `hash`, any occurrence, nearest to `pos` (ties → lowest index); (4) Sørensen–Dice ≥ 0.8 on normalized text among candidates of the same `kind`, restricted first to the same section, then the whole document, ties → highest score then lowest index; (5) `orphans`, shown in an "Unattached" sidebar section (drag onto a sentence, or delete).
- **Duplicate limit, stated plainly.** Two byte-identical sentences (or headings with identical surroundings) are indistinguishable in the Markdown. **In-app** operations (Reorder drag, Outline move) update anchors live, so identity follows the logical item. After an **external** edit that swaps such duplicates, the file contains no evidence of which one moved, so resolution is position-based by construction: the anchor stays with the occurrence at its `pos`. The PRD does not claim otherwise, and the sidebar shows a small "duplicate" badge on such cards so the user knows. Tests cover: in-app swap of two identical sentences keeps each variant on its logical sentence; external swap (file rewritten on disk) keeps each variant at its position; identical headings likewise.
- Coach entries have `scope` ∈ {`sentence`, `paragraph`} only and a non-null anchor of the matching kind (zod-enforced); there is no essay scope in v1 (§5).
- The sidecar is optional. Deleting it loses questions/variants, never content. Front-matter `title`/`question` are mirrored; sidecar wins on conflict.

### 6.3 Modes are views, not states of the document

All four modes render the same store. Switching modes never mutates the document.

- **Outline**: left sidebar section tree (drag to reorder / nest = `setHeadingDepth` + `moveSection`). Main pane lists sections as questions (question text if set, else heading text) with inline question fields; topic question field at top; "New question" appends a heading (text = question) + empty paragraph.
- **Produce**: sidebars hidden, editor centered at 68ch, each heading shows its question in a muted 0.85em line above it (read-only; click → Outline). Optional typewriter scrolling. Esc returns to the previous mode.
- **Rewrite**: right sidebar lists sentences of the cursor's paragraph (expand-to-section toggle). Per sentence: original, variants list, add-variant textarea (Cmd/Ctrl+Enter adds and selects), radio, "Use this" → `replaceSentence`, collapsed history.
- **Reorder**: right sidebar with sentence chips (current paragraph), paragraph cards (current section), section tree; all dnd-kit sortable with keyboard support; each drop is one undo step.
- **Source toggle** (Cmd/Ctrl+/): swaps ProseMirror ↔ CodeMirror over the same canonical Markdown; cursor mapped by (line, ch) ↔ PM position through the formatter's position map.

### 6.4 Rust side (`src-tauri`) — the complete IPC surface

`open_folder`, `list_tree`, `read_doc`, `write_doc` (temp + atomic rename), `read_sidecar`, `write_sidecar`, `new_file`, `rename_file` (doc + sidecar + `assets/<stem>` together), `delete_to_trash` (via `TrashBackend` trait; test build injects a recording fake), `reveal_in_folder`, `watch_folder` (notify → event `fs:changed`), `save_image` (bytes → `assets/<docstem>/<yyyyMMdd-HHmmss>.<ext>`), `export` (spawn pandoc sidecar, stream stderr), `get_settings`/`set_settings`, `set_coach_key` / `has_coach_key` / `clear_coach_key` (the secret never crosses IPC to the frontend; `has_coach_key` returns only a boolean and a backend-status enum `available | locked | unavailable`; Rust reads the secret internally when calling the endpoint), `coach_complete` (proxy; streams tokens). Nothing else.

**Workspace-root authority.** `tauri-plugin-fs` scopes protect only that plugin's commands; every command above that takes a path is custom Rust and enforces its own scope. A single `WorkspaceRoot` value (set by `open_folder`, canonicalised with symlinks resolved) is the authority. **Contract**: every command except `open_folder` takes a **workspace-relative** path; an absolute path is rejected with `InvalidPath` before any filesystem access. The command joins the relative path to the root, canonicalises the deepest existing ancestor, and rejects any result not strictly beneath the root with `PathOutsideWorkspace`. The empty relative path (the root itself) is valid only for `list_tree` and `watch_folder`; every other command returns `InvalidPath` for it. On case-insensitive filesystems the comparison uses the canonicalised (OS-case-folded) form so `../ESSAYS/x` cannot slip past a case-sensitive check. Covered by cargo tests: relative-inside, `..` traversal, absolute (inside and outside — both `InvalidPath`), the root itself per command, a symlink inside the workspace pointing outside, a nonexistent target whose parent is such a symlink, Windows reparse points/junctions (`#[cfg(windows)]`), case-folded escape, and `export` output paths. `save_image` names files `<yyyyMMdd-HHmmss>-<6 random base36>.<ext>` so two pastes in one second cannot collide.

Images: `assetProtocol.enable = true`, `assetProtocol.scope` extended at runtime to the opened folder and persisted with `tauri-plugin-persisted-scope`; CSP `img-src 'self' asset: http://asset.localhost data:`; every image node's `src` goes through `convertFileSrc(absolutePath)` at render time, where `absolutePath = resolve(docDir, relativeSrc)`.

### 6.5 Undo model

The document store owns one undo stack of `{root, sidecar}` snapshots (structurally shared, capped at 500). Every committed mutation pushes: a coalesced typing burst (ProseMirror transactions within 1 s of each other merge), a CodeMirror edit burst (same rule), each mode mutation (rewrite "Use this", reorder drop, outline move/nest, question edit), and a source/rendered toggle ends the current coalescing group without pushing a new snapshot (a toggle is not an edit; the first Undo after a toggle undoes the last real edit). Cmd/Ctrl+Z / Shift+Z are bound at the store level in both views. **Undoing "Use this" restores both the sentence and the sidecar's `chosen` field** (answers open question 2 by default; Michael can override before Locked). ProseMirror's `history` plugin and CodeMirror's `history` extension are not installed.

Review findings that reveal a *class* of mistake are written to `docs/lessons.md` in the reconciliation step (§10.3).

Every task has an `execution` mode (RUNNER-SPEC §2): `bootstrap` (0.0 only, interactive on the host), `loop`, `loop-external`, `reviewer`, `interactive-principal`, `replan`, `human`, `runner`. `blockedOnHuman: true` appears only on `human` tasks. REJECT (approval) and GATE-FAILED (ci) leave dependents blocked and raise a plan request (`plan.<gate>.r<n>`, first-class runtime state) that I resolve with one planning commit adding fix tasks and replacement tasks — CI repairs in the `.g<n>` namespace, approval and review revisions in `.r<n>`; execution reruns of the same gate against the same SHA are `a<n>` attempts, exist only for transient failures, and never change ids (a workflow-file fix changes the SHA and is therefore a `.g<n>` repair); every `needsCI` execution pushes an immutable `ci/<id>/a<n>` ref and the only tag ever created is the final release tag at close; every consumer reads gate evidence through `accepted.json`; passed tasks are never mutated (RUNNER-SPEC §2). The phase's reconciliation copies records with a `recordTarget` into `DECISIONS.md`; CI gates are `recordPolicy: evidence-only`. RC packaging runs on such refs too, so the only tag ever created is the final release tag at `N.close`. Because gates produce no commits and the verifier is the last commit-producing task before a review attempt, the SHA CI tested (`verification_sha`, from the attempt's recorded `verifier_id`) is the SHA the reviewers see (`implementation_sha`); the runner asserts it for every attempt. For release phases the verifier's CI gate is also the **final-package gate**: it builds the installers from the exact product tree that will be tagged (the tagged commit differs only by review documents), and `N.close` resolves the approved candidate from the newest passing attempt's verifier gate and requires its SHA to equal that attempt's `verification_sha`; the manual publication procedure compares the packages rebuilt from the tagged commit against those digests.

## 8. Task list

Conventions: `id` is `phase.n`. Each task is one agent iteration (~20–40 tool calls), ends in one commit `task(<id>): <description>`, and leaves `pnpm test`, `pnpm lint`, `cargo test` green. Dependency readiness determines eligibility, but the runner starts exactly one implementation task at a time; the only parallel work is a review set's three reviewers. ## 9. Agent operating rules (apply to every task)

1. **Disposable worktree, own branch.** Every agent works in its own worktree on its own `task/<id>` branch cut from the current `phase/N` head, never on the phase branch directly and never on Michael's live checkout. Integration into `phase/N` is done by `ralph.sh`, not by the agent (§10.2). Merges to `main` happen only after the phase review set reconciles to pass.
2. **One task, one acceptance commit.** On its task branch an agent may make any number of `wip(<id>): …` commits (failed attempts, clean-break notes, recovery). At integration `ralph.sh` squashes the task branch into exactly one commit on `phase/N`: `task(<id>): <description>` with the acceptance criteria and `Depends-on:` closure in the body; the wip history is preserved as a tag `wip/<id>` for forensics and never lands on `phase/N`. `reviewer` and `human` tasks produce no commit (RUNNER-SPEC §2); their completion is an evidence file. If a task's acceptance genuinely needs two integration commits, it was two tasks.
3. **Green before integration.** `pnpm test`, `pnpm lint`, `cargo test` pass on the task branch (stop-check), and again on the squashed candidate in a detached worktree before `phase/N` is advanced; state flips to `passed` only after the ref update succeeds (RUNNER-SPEC §4). Never `.skip()` a test to get green; file a task instead. Applies from task 0.1 onward.
4. **Scope is the task text.** No unrequested features, no "while I'm here" refactors, no dependencies beyond §4 without a DECISIONS.md note and Michael's OK.
5. **Reviewer independence.** Every phase is reviewed by three separate fresh-context agents — Claude Opus, GPT-5.6 Sol, Grok 4.6 — none of which has the implementing session's context. Reviewers read PRD + RUNNER-SPEC + lessons + the phase diff + accepted evidence, try to falsify the gate, and cannot edit code: the snapshot worktree is mounted read-only; Claude and Sol get a throwaway scratch copy in which to build and run tests, whose `git status --porcelain` (ignored files excluded) must be empty at exit and which is deleted afterwards; Grok evaluates the read-only tree and the supplied logs only. The only writable persistent path is `/logs/reviews/<phase>/r<k>/<reviewer>/`. Between phase reviews, a task's own tests are its only check; no per-commit review.
6. **Reversibility.** `phase/N` is a linear sequence of one-commit-per-task; it is never squashed further and never rewritten once a task is integrated. Each acceptance commit body lists its dependency closure (`Depends-on: 0.7, 0.8`). Reverting a task means reverting it **together with its transitive dependents in reverse integration order**; that combined revert must leave tests green. A lone revert of a task with integrated dependents is not expected to build.
7. **Michael reads verdicts, not diffs.** Every report leads with pass/fail per gate criterion, test counts, and the three riskiest things; the diff link comes last.
8. **Human gates are real.** `blockedOnHuman` tasks pause the graph. An agent never writes a DECISIONS entry attributed to Michael.
9. **Model allocation.** Opus: `core`, `editor`, sidecar/anchoring, undo, Rewrite/Reorder/Outline, watcher/conflict logic, the coach client and filter, the retrospective. Sonnet: scaffolding, CI, fixtures, settings, file tree, images, Produce, export, sidecar packaging, release, platform measurement, the claude-cli provider. Review sets: Claude Opus + Sol + Grok, reconciled by me. A Sonnet agent that hits an architectural decision stops and files a note rather than deciding.
10. **Container by default, four host exceptions.** Implementation tasks and normal reviews run only in the container via `docker compose run claude-task <id>` / `claude-review | codex-review | grok-review <phase> <attempt>`. The host exceptions are exactly: task 0.0 (`bootstrap`), human gates via `scripts/gate.sh`, the host-side scripts (`fetch-ci-logs.sh`, `bootstrap.sh`, `ralph.sh`), and the Grok fallback when its login state cannot be mounted (read-only worktree at `implementation_sha`, writes only its report directory). The host checkout is never an agent's working copy.
11. **Record before you stop.** Every iteration appends to `docs/progress/journal-main.md` (never to the generated `docs/progress.md`, and never its own commit SHA) and, when it learned something, `docs/lessons.md`, then commits on its task branch (`wip(<id>)`) — including failed iterations (§10.3), so the next iteration on that task inherits the notes. An iteration that ends without a journal entry is a bug in the loop, not a choice.
12. **The container never pushes.** No git credentials exist in the image. Michael pushes exact SHAs, `main`, and tags from the host through `scripts/gate.sh`; CI results reach the evidence directory (`.evidence/ci/<id>/` on the host, `/logs/ci/<id>/` in containers) via `scripts/fetch-ci-logs.sh` run on the host. Any task whose acceptance needs a remote carries `needsCI: true` and is expanded into an agent part and a `<id>h` CI gate (§7).

## 10. Execution model

### 10.1 Workflow choice (per the workflow-selection framework)

"Done" is machine-verifiable and the task list is complete, so **each phase runs as a Ralph loop** over `ralph/tasks.json`, one iteration per task, fresh context every iteration, inside the container. The exceptions are decided per task, not per phase: `blockedOnHuman` tasks pause the loop (stop-check exits with `HUMAN_GATE <id>`), the spike decision (4.0r) and the re-planning task (6.2r) are `interactive-principal` tasks because their output is a judgement not a test, and the stop signals of RUNNER-SPEC §11 drop the loop into an interactive session with me. Implementation tasks run strictly sequentially, one at a time, within and across phases; the only parallelism is the three reviewers of a review set, from the same snapshot (RUNNER-SPEC design rule).

Loop parameters to start: `--max-turns 50` for implementation tasks, 30 for setup/config, 15 iterations per run, review the first 3 transcripts in `/logs/tasks/` before letting it run unattended. Kill triggers (RUNNER-SPEC §11): `STUCK`, `CONFLICT`, `INTEGRATION-FAILED`, no journal entry for an iteration, or no wip commit in two iterations.

**Pre-loop hygiene** (adapted from quote-engine's PROMPT.md): every iteration begins with `git status` in its task worktree; a dirty tree from a crashed iteration is committed first as `wip(<id>): recovery of uncommitted changes` so nothing is lost. There is no per-iteration rebase: implementation is sequential, so the branch base cannot move, and the only rebase is the one inside the integration transaction (RUNNER-SPEC §4); a conflict there stops the loop with `CONFLICT <id>`.

**What a spike is.** A spike is a timeboxed, throwaway investigation whose only deliverable is a decision document, never code that ships: "try X for one iteration, measure Y, write the answer down." We use one here (4.0: can pandoc + typst embed relative images on all three OSes?) because the answer changes the export design and is cheaper to learn in an hour than to discover in the export task. A spike lives on a branch that is deleted after its document merges, so nothing half-built leaks into the product.

### 10.2 Container, branches, integration, reviews, gates, phase close

The full protocol is `docs/RUNNER-SPEC.md` (v1.7), which is canonical; this is the summary. Phases and implementation tasks are **strictly sequential** and there is **one lock** (`/work/.locks/ralph`); the only parallelism is the three reviewers of a review set. `ralph/tasks.json` is an immutable specification; all status lives in `.evidence/state/` and is written only under the lock, atomically. Evidence (transcripts, CI logs and artifacts, reviewer reports, human-gate records, close records, external-repo state) lives under `.evidence/` on the host, mounted as `/logs` in every container, never inside a worktree.

Task 0.0 is the single `bootstrap` exception: it runs interactively on the host after the `docs/PREFLIGHT.md` checklist, creates the image and the runner, makes the initial commit, and `bootstrap.sh` initialises state with 0.0 passed; everything from 0.1 runs in the container. Every `loop` task works on `task/<id>` cut from its `targetBranch`, commits `wip(<id>)` freely (rebasing only at integration), and appends to `docs/progress/journal-main.md` (never `progress.md`, never its own SHA). Branches move only through the integration transaction: read `expected_old` → rebase → build the squashed candidate without moving the branch → test it in a detached worktree → `update-ref` with `expected_old` → flip state → regenerate `/logs/state/summary.md`. Failure states (`blocked`, `integration-failed`, `CONFLICT`) have explicit recovery commands (`retry`, `resume`, `resolve-conflict`, `abandon`), all audited; a rejected approval gate or a failed CI gate raises a plan request that I resolve with one planning commit (fix tasks and replacement tasks with new ids) rather than mutating passed tasks. The runner ends at `N.close`: publishing a tag is Michael's manual procedure (`docs/PUBLISH.md` — push, watch `release.yml`, compare the rebuilt artifacts' digests against the candidate gate's `accepted.json`, record the result in `.evidence/publish/<tag>/` and DECISIONS); a broken release workflow cannot be fixed for an existing tag and ships its fix in the next phase; the v1 runner has no patch or publication machinery by design. Crash safety is detection, not journaling: there are no intent files; every integration tags `candidate/<id>` before its `update-ref`, every CI attempt writes `run.json` before it waits, `ralph.sh doctor` reports every inconsistency between refs, tags, evidence and state and names the one `admin` command that repairs it (`admin mark-integrated`, `admin retry`, `admin resolve-request`, `gate.sh --resume`), and `ralph.sh run` refuses to start until `doctor` is clean. RC packaging runs on immutable ci refs, so no tag exists before the final one.

Reviews: each attempt `r<k>` (from `r0`) has its own verifier (`N.verify`, then `N.verify.r<k+1>` after a FAIL) whose CI gate runs on an immutable `ci/<id>/a<n>` ref; gates produce no commits, so the SHA CI tested equals the `implementation_sha` the three reviewers see (asserted by the runner per attempt). The reconciliation records a machine-readable verdict separate from its task status; a FAIL grows the graph (fixes, new verifier, new attempt) and `N.close` requires the newest verdict to be PASS. Reviewers run in parallel from read-only worktrees at that SHA, write only to `/logs/reviews/<phase>/r<k>/<reviewer>/`, and never see each other's reports; Claude and Sol cold-build a local clone of `/work` in scratch. Reconciliation is one commit (reports, human records into `DECISIONS.md` by `recordTarget`, verdict, lessons, regenerated `progress.md`, release-notes finalisation) and is a planning commit, so `sync-state` follows it and any fix tasks plus a review attempt `<id>.rN` enter runtime state. `N.close` is transactional and idempotent: it checks the source branch against the passing reconciliation, that only docs changed since `implementation_sha`, and that `main` equals the phase's recorded base; tests the proposed commit detached; checks the close-time release invariant (version fields; the candidate resolved from the newest passing attempt's verifier gate equals that attempt's `verification_sha`); writes a versioned intent record listing every ref with expected-old and intended OIDs; then moves `main`, the tag and the `nextBranch` in one ref transaction and only afterwards writes the `nextPhase` record and finalises `closes/N.json` (a terminal close writes no phase record) — a crashed close is re-run safely. The publication invariant (workflow run, artifacts, checksums, URL and tag all naming one SHA, digests equal to the candidate gate's) is checked by hand per `docs/PUBLISH.md`. Topology: `phase/0→1→2→3→4→6` into `main`, `v0.1.0` at `6.close`, then `phase/5` (coach + retrospective) from `main` starting at `6.close` (publication is outside the graph), `v0.2.0` at `5.close`.

Entry points (RUNNER-SPEC §11): `ralph/bootstrap.sh` (host, once); `ralph.sh run | retry | resume | resolve-conflict | abandon | plan | plan-retry | plan-abandon | rerun | close | sync-state | status | doctor | admin mark-integrated | admin retry | admin resolve-request`; `docker compose run claude-task <id>`, `claude-review | codex-review | grok-review <phase> <attempt>` (`grok -p "<prompt>" --output-format streaming-json`, read-only role); `scripts/gate.sh <id> [--resume a<n>] | rerun <id> | abandon <id> a<n> | gc` (host; executes `ci` objects, never prose); `scripts/fetch-ci-logs.sh` (host). No API keys, no git credentials, no SSH agent in any container.

### 10.3 Compound engineering: how the project gets smarter as it goes

**Journals plus generated summaries (RUNNER-SPEC §10).** Iteration records are one append-only journal, `docs/progress/journal-main.md`, entries keyed `[<task-id>] <ISO timestamp>`; nobody edits old lines, corrections are new lines. `/logs/state/summary.md` (outside git) is regenerated by `ralph.sh` after every integration and is what agents orient from; `docs/progress.md` (tracked) is regenerated only in reconciliation commits as the phase summary, so no task commit ever carries its own SHA and no mutable region meets a merge. `docs/lessons.md` is purely append-only and keeps `merge=union`; it is the only union-merged file. Agents read `/logs/state/summary.md` for orientation and never write `progress.md`; they append to their journal. Older journal entries are never pruned (the loop does not read them), which removes the archive step and the context-starvation risk at once.

**Lessons have a lifecycle.** A lesson enters as `[<task-id>] LESSON: <root cause> → <what to do instead>`. `scripts/promote-lessons.ts` (run at every phase review) flags any lesson whose keywords recur in ≥ 2 entries; I turn those into a rule in `CLAUDE.md`/`AGENTS.md` (which every iteration reads) and mark the lesson `PROMOTED`. Lessons that never recur stay lessons. Rules that stop being triggered for a whole phase get demoted back to lessons to keep `CLAUDE.md` short. Reviewer findings that describe a class of mistake ("acceptance criteria referenced a file no task creates") go straight into `lessons.md` under `[review-N]`.

**Every bug buys three things.** A regression test, a lesson, and — if it came from a reviewer or from Michael — a tighter acceptance-criteria pattern in `BUILD-DEFAULTS.md` so the *next* PRD can't make the same mistake. The retrospective's evidence cutoff is before Phase 5's own review; that review's class-level lessons go to `docs/RETRO-CARRYFORWARD.md` and are applied to BUILD-DEFAULTS at the start of the next project (RUNNER-SPEC §9).

**Trajectory engineering, the cheap version.** Ralph's clean-break protocol already forks the timeline at the iteration level: if an agent debugs for more than 5 tool calls, it writes root cause + fix (or hypotheses) to `lessons.md`, commits, and stops, so the next iteration begins in a world where the bug is already solved and never sees the failing trajectory. We extend that one level up: when a bug is found in phase N+1 that originated in task X of phase N, the fix goes in *as if it were part of task X* — the lesson is written in task X's terms, the acceptance criterion of task X is amended in `tasks.json` and PRD §8 so the loop would have caught it, and the regression test lands next to X's tests. We do not rewind and re-run the phase; the transcripts in `logs/` are kept so I can read the exact decision point when writing the lesson. Full replay from the fork point is on the table for a class-level failure (e.g. the editor engine turning out wrong) and is a decision I bring to Michael, not something the loop does on its own.

**Pre-mortem per phase.** Before a phase's loop starts (after `N-1.close`), I read `lessons.md` and the previous phase's three reviews and write a 5-line "watch-outs" block at the top of that phase's `PROMPT.md`. It is the only phase-specific prose in the prompt.

**The defaults travel.** `BUILD-DEFAULTS.md` lives in its own repo (`MLSavage/build-defaults`) and is copied into each new project at task 0.0. Tasks post.1–post.4 are the retrospective that diffs what we wish we had known into it, with evidence, so the next project starts where this one ended. It is the file Michael pulls up instead of remembering.

### 10.4 Metrics recorded in `progress.md` (so we can see the compounding)

Per task (from the journals): iterations to pass, tool calls used, whether the first attempt passed, whether a reviewer overturned it. Per phase: review findings by severity, lessons written, lessons promoted, kill-triggers hit. Task post.1 tabulates these. The numbers that matter: first-attempt pass rate should rise phase over phase, and review blockers per phase should fall; if they don't, the lessons aren't reaching the prompts.

### 10.5 Reviewer protocol (Claude Opus, Sol, Grok)

Input to all three: `docs/PRD.md`, `docs/RUNNER-SPEC.md`, `docs/lessons.md`, `git diff <phase_base_sha>...<implementation_sha>` (both recorded in `/logs/reviews/<phase>/`), `/logs/ci/<verifier_id>/accepted/` (the attempt's own verifier) and the phase's other `/logs/ci/<id>/accepted/`, `/logs/human/<id>/accepted.json` and `/logs/tasks/` directories, and the gate table row for the phase. Claude and Sol run the suite themselves in their throwaway scratch copy (§9.5); Grok evaluates the read-only snapshot and the supplied logs only, citing `/logs/ci/<verifier_id>/accepted/` (the attempt's own verifier) for the cold build. All three start from the same `implementation_sha` and none sees another's report before reconciliation. Output template (`docs/reviews/TEMPLATE.md`): gate criterion table (pass/fail/unverifiable + evidence), test counts, coverage delta, up to 20 numbered findings with severity / file:line / concrete fix, three riskiest things, and a "class-level lessons" list. **When outside eyes look, and why at those points.** (1) At the PRD, before any code — the cheapest place to catch a wrong assumption; eight audits paid for themselves. (2) At the end of Phase 0 — the core model and the runner are the foundation every later phase imports. (3) At every phase gate thereafter. We do not review per commit: commits are atomic, so the phase is the smallest unit whose review is worth three models' time; the trade-off is latency, accepted. I reconcile the three reports in the `<id>.r<k>d` task (verdict in DECISIONS, follow-ups inserted into PRD §8 and tasks.json together, validator run): where two or more agree, act; where they disagree, the reviewer with reproducible evidence wins and the disagreement is itself recorded in `lessons.md` as data about each reviewer's blind spots (this is how we learn which reviewer to trust for what).

## 11. Resolved planning decisions and stated fallbacks

All former open questions are recorded in `docs/DECISIONS.md#000-lock-decisions`: (1) the fixture essay is Michael's own, supplied via `docs/fixture-essay.md` as a PREFLIGHT item (the agent writes a neutral one only if that item is marked "agent writes"); (2) Cmd/Ctrl+Z after "Use this" restores both the sentence and the sidebar choice (§6.5), accepted as the default to be revisited only from real use. Stated fallbacks, not tasks: if WebKitGTK parity fails in Phase 6, Linux ships on Electron with the same frontend (decision at 6.2r); if Typst cannot embed images on some OS, the pipeline in DECISIONS #004 applies; if `claude -p` leaves subscription coverage, the `claude-cli` coach provider is removed and the local-model provider remains the only one.
